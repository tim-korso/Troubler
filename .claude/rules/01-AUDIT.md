# Troubler 审计规则

> 跨所有审计项目生效。这是 Troubler 的执行框架。

## 审计四阶段

### 0. 架构审讯
画出完整数据流图。不知道数据怎么走，就问不出来 bug 在哪里。
「从输入到输出，每一步的数据格式和传递方式是什么？」
「哪些步骤是自动的，哪些是手动的？」
「中间产物在哪里？我能看到吗？」

### 1. 边界审讯
对数据流图中每一个箭头追问「这里什么情况下会断」：
- 如果上游输出为空，下游怎么反应？
- 如果上游输出格式变了，下游能检测到吗？
- dev 和 prod 环境下行为一样吗？

### 2. 产物审讯
不看代码，看构建结果：
- `ls dist/` — 文件类型齐全吗？
- 构建前后 hash 对比 — 改了的文件对应 hash 变了吗？
- 产物体积是否合理 — CSS=0KB？
- 抽检产物内容 — grep 关键字符串
- 截图像素分析 — 内容密度 > 1%

### 3. 社区校准
每个技术选择都要有理由。没有理由的偏离 = bug。
「社区对这个场景的推荐方案是什么？」
「你选了什么？为什么？」
「你的理由成立吗？」

## 通用弹药（领域无关问题）
```
□ 数据流图画得出来吗？
□ 哪些步骤「觉得应该没问题」但没验证过？
□ 构建产物在哪里？
□ 上次改代码后构建 hash 变了吗？
□ dev 和 prod 行为有差异吗？
□ 上游数据为空时下游怎么反应？
□ 用了哪些社区标准方案？哪些是自创的？为什么？
□ 最后部署的版本实际看过运行效果吗？
```

## 审计节奏
```
第一轮 (广): 架构审讯 + 产物快检 → 列出可疑边界
第二轮 (深): 可疑边界深挖 → 至少 3 层追问 → 要求产物证据
第三轮 (修): 追踪修复 → 重新跑产物检查 → 确认 hash 变了
第四轮 (防): bug → 防护规则 → 更新 GUARDRAILS.md
```

## 约束
- 不写代码，只审计
- 每个发现必须有产物证据
- 量化结论：通过/不通过/有条件通过
- 同一个 bug 不能出现第二次
